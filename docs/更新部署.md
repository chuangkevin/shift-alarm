# 更新部署

新版韌體目錄為 `firmware-next`。目前裝置已部署 0.3.1。舊 `firmware` 為先前 PlatformIO 版本，不可拿來當新版更新。

## 首次安裝

首次從原廠或 0.1.x 遷移，需要 USB 安裝新版引導程式、分區表與應用程式。先識別目前連接的晶片／MAC／Flash／PSRAM，對這一台保存完整備份；不可將另一台的原廠備份或 Tailnet 身分當作這一台的備份。Flash 中可能有密碼與身分私鑰，備份與帶憑證韌體不得公開。

目前原機已經使用原廠 [線上燒錄頁](https://upload.nologo.tech/) 恢復；先前 USB 中斷原因未確認。此事不代表已證實硬體燒毀，也不代表之後寫入保證沒有中斷。出現寫入錯誤就停止，先確認連接與原廠救援模式。

編譯測試與元件測試，不等同首次安裝或實機更新測試。必須完成硬體驗收後，才可記錄為可用版本。

## 後續更新

1. 修改程式並提高 `firmware-next/CMakeLists.txt` 的三段數字版本。板型固定 `xingzhi-cube-1.54tft-wifi`。
2. 使用 ESP-IDF 5.3.2／Arduino 3.1.3 建置，執行後端、OTA 政策、代理串流及 Tailnet 測試並完成審查。保留建置設定與摘要。
   首次部署時將 `firmware-next/main/provisioning.example.h` 複製為被 Git 排除的 `provisioning.h`，填入後端 `DEVICE_TOKEN` 並移除範本的編譯阻擋行；不填入 Wi-Fi 密碼、New API 金鑰或另一台的 Tailnet 身分。`provisioning.h` 與其建置出的韌體均視為私密檔案。
3. 使用應用程式 `.bin`，不能使用整片 Flash 備份、引導程式或合併映像。檔案最多 4 MiB。
4. 將應用程式與 `deploy/publish_firmware.py` 傳至後端主機的私有目錄。以容器的同一 UID `1000` 執行發布，確保容器可讀取；工具建立的目錄為 `0700`、檔案為 `0600`。

```sh
python3 deploy/publish_firmware.py /私有路徑/應用程式.bin --release-dir /home/kevin/DockerCompose/shift-alarm/data/releases
```

工具驗證板型、版本、分段校驗、內建 SHA-256 與大小，先保存不可變摘要檔案，再原子切換 `active.json`。版本必須遞增；同一映像重跑不會重複改動。此步僅發布，裝置不會自行安裝。

5. 在裝置本地「裝置設定 → 裝置更新」確認供電穩定，再按「檢查並安裝已發布版本」。此供電確認來自操作者，裝置未量測電壓。
6. 裝置驗證清單 HMAC、映像 SHA-256、板型與版本，只寫入備用應用程式分區。響鈴中、貪睡中、未校時、未有排程狀態或五分鐘內有鬧鐘時不啟用更新。
7. 新版通過本機初始化、自測與保存資料恢復後才確認版本。更新寫入階段的失敗會保留舊版；開機失敗回退需要已具備回退配置與有效舊版的引導程式。首次安裝不具有已驗證的舊版回退保障。

Wi-Fi、方向與排程保存在獨立設定分區；正常 OTA 不擦除此分區，不啟用 eFuse anti-rollback。Tailnet 身分保存在 NVS，重新授權只更新必要的節點憑證。

後續更新通道規定與預檢／啟動命令見 [Tailscale OTA](Tailscale-OTA.md)。裝置必須實際可經原生 Tailscale 到達後端；不得以同 LAN 優先路由替代。既有本地更新頁只是操作介面，更新檔的下載通道仍須遵守此限制。


## 可重現的 USB 操作

以下以 ESP-IDF 5.3.2 的 Python 環境與 esptool 4.x 為準；連接埠請依當次實際裝置更換。先關閉占用序列埠的監視器。不要同時執行兩個刷寫程序。

```sh
python -m serial.tools.list_ports
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 chip_id
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 flash_id
# 私有目錄內備份本次連接的 16 MiB 裝置；不得公開此檔。
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 \
  --baud 460800 --after no_reset read_flash 0x0 0x1000000 device-private-backup.bin
chmod 600 device-private-backup.bin
idf.py -C firmware-next build
```

保存 `sdkconfig.defaults` 的 PPP 支援設定及 ESP-netif 相容性檢查。此設定用來隔離 SDK client-data，沒有啟用 PPP 網路；移除會重現先前的非 ESP-netif 指標解讀問題。不要停用編譯保護來繞過錯誤。

**僅第一次從原廠／舊分區遷移**，核對建置產物與分區配置後，在 build 目錄使用當次生成的 `flash_args`。這會寫入引導程式、分區表與初始 OTA 選擇資料，不能用於一般更新：

```sh
cd firmware-next/build
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 \
  --baud 460800 --before default_reset --after no_reset write_flash @flash_args
```

已有雙 OTA 分區的裝置，日常更新使用 [Tailscale OTA 工具](Tailscale-OTA.md)。必須以 USB 修復時，先讀取 0xe000 起 0x2000 位元組的 OTA 選擇資料並保存。兩個 4096 位元組 sector 的 sequence、state、CRC 分別位於 0、24、28。CRC 為 `binascii.crc32(sequence的4位元組little-endian編碼, 0xffffffff)`。只在兩筆狀態及執行分區可明確核對時繼續；損毀、待確認、回退或計數繞回情形不能猜測。

核對分區表後，先寫**非執行中**的 app 分區，等待 esptool 回報雜湊驗證成功；再寫入一個 OTA 選擇 sector，填入對應新 sequence、state=0（NEW）、CRC，其餘填 0xff。`(sequence-1)%2` 對應 app0/app1。不得覆蓋 NVS、另一個 OTA 選擇 sector、引導程式或分區表。實測 0.3.0 是 app1 0x410000、sequence 10；這只是該次紀錄，不是下次可盲抄的目標位址。

本板已驗證的啟動方式如下；保持 RTS 為 false，不使用先前造成啟動狀態混淆的 `hard_reset`／`run`。讀取啟動訊息後關閉連接埠：

```python
import serial, time
p = serial.Serial()
p.port = '/dev/cu.usbmodem1101'
p.baudrate = 115200
p.timeout = 0.2
p.dtr = False
p.rts = False
p.open()
p.dtr = True
until = time.monotonic() + 30
while time.monotonic() < until:
    # 訊息可能包含私人網路資訊，請在私有終端檢視。
    print(p.read(8192).decode(errors='replace'), end='')
p.close()
```

成功寫入不等於功能驗收：確認版本、螢幕、網路、方向、班表、校時與按鈕，再實測 Tailscale 資料通道。2026-09-13 的 0.3.1 已用 USB 部署並確認版本、Wi-Fi、方向、班表與校時；完整 OTA 安裝流程仍待另行驗證。
