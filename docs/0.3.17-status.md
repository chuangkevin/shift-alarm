# 0.3.17 內容與 OTA 實測結果

> 後續 `docs/ota-research.md` 的程式碼追查已推翻本文件當時對「Range／續傳缺陷」的判定。以下保留實測現象；根因應以研究文件為準：傳輸中的安全護欄會丟棄整個 transfer，而第二台當次觸發的確切護欄仍待序列診斷確認。

## 這版改了什麼

- 手機端上傳：圖片上限 `1600px → 1100px`、JPEG `q0.85 → q0.8`。
- 手機端等待：整體中止 `60s → 240s`；辨識前健康檢查 `8s → 60s`（原本 8 秒會在慢速 relay 上直接中止，是先前畫面上錯誤訊息的來源）。
- 後端：辨識上限 `45s → 180s`（可用 `RECOGNITION_SECONDS` 覆寫，範圍 30–200）；圖片重編碼由 `2200px / q92` 改為 `1600px / q80`，不再把手機壓好的圖撐大。
- 版本：韌體 `0.3.17`、後端 `0.1.6`。

## OTA 實測失敗

- 下載閘門被 `backend-poll-busy` 長期佔住：51 次取樣只有 3 次 `canDownload=true`，因為每輪輪詢在慢速 relay 上幾乎一直在 in-flight。
- 用連續 POST 抓到空檔後成功啟動下載（`202 已開始下載`）。
- 下載只寫入 `4096 bytes` 就中止：`lastReason=resume-failed`、`lastHttpStatus=200`、`reconnectCount=0`。
- 後端已排除：Range 與完整串流都正常（同上）。
- 當時曾推測裝置續傳請求未取得 `206`，但 `lastHttpStatus=200` 與 `reconnectCount=0` 不能證明曾送出 Range 重連。後續確認程式會在護欄瞬斷時先丟棄 transfer，再把下一次寫入錯誤統一記成 `resume-failed`；因此不可再把這次記為已證實的 Range 缺陷。
- 另有限制：OTA 下載總期限為 600 秒，此 relay 速率下 1.6 MB 本來就難以在期限內完成。
