# 更新部署

新版韌體目錄為 `firmware-next`，版本 0.2.0。舊 `firmware` 為先前 PlatformIO 版本，不可拿來當新版更新。

## 首次安裝

首次從原廠或 0.1.x 遷移，需要 USB 安裝新版引導程式、分區表與應用程式。先識別目前連接的晶片／MAC／Flash／PSRAM，對這一台保存完整備份；不可將另一台的原廠備份或 Tailnet 身分當作這一台的備份。Flash 中可能有密碼與身分私鑰，備份與帶憑證韌體不得公開。

目前原機已經使用原廠 [線上燒錄頁](https://upload.nologo.tech/) 恢復；先前 USB 中斷原因未確認。此事不代表已證實硬體燒毀，也不代表之後寫入保證沒有中斷。出現寫入錯誤就停止，先確認連接與原廠救援模式。

應用程式版本 0.2.0 的編譯測試與元件測試，不等同首次安裝或實機更新測試。必須完成硬體驗收後，才可記錄為可用版本。

## 後續更新

1. 修改程式並提高 `firmware-next/CMakeLists.txt` 的三段數字版本。板型固定 `xingzhi-cube-1.54tft-wifi`。
2. 使用 ESP-IDF 5.3.2／Arduino 3.1.3 建置，執行後端、OTA 政策、代理串流及 Tailnet 測試並完成審查。保留建置設定與摘要。
3. 使用應用程式 `.bin`，不能使用整片 Flash 備份、引導程式或合併映像。檔案最多 4 MiB。
4. 將應用程式與 `deploy/publish_firmware.py` 傳至後端主機的私有目錄。以容器的同一 UID `1000` 執行發布，確保容器可讀取；工具建立的目錄為 `0700`、檔案為 `0600`。

```sh
python3 deploy/publish_firmware.py /私有路徑/應用程式.bin --release-dir /home/kevin/DockerCompose/shift-alarm/data/releases
```

工具驗證板型、版本、分段校驗、內建 SHA-256 與大小，先保存不可變摘要檔案，再原子切換 `active.json`。版本必須遞增；同一映像重跑不會重複改動。此步僅發布，裝置不會自行安裝。

5. 在裝置本地「裝置設定 → 裝置更新」確認供電穩定，再按「檢查並安裝已發布版本」。此供電確認來自操作者，裝置未量測電壓。
6. 裝置驗證清單 HMAC、映像 SHA-256、板型與版本，只寫入備用應用程式分區。響鈴中、貪睡中、未校時、未有排程狀態或五分鐘內有鬧鐘時不啟用更新。
7. 新版通過本機初始化、自測與保存資料恢復後才確認版本。更新寫入階段的失敗會保留舊版；開機失敗回退需要已具備回退配置與有效舊版的引導程式。首次安裝不具有已驗證的舊版回退保障。

Wi-Fi、方向與排程保存在獨立設定分區；正常 OTA 不擦除此分區，不啟用 eFuse anti-rollback。Tailnet 身分保存在 NVS，重新授權只更新必要的節點憑證。
