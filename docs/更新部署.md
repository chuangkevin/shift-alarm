# 更新部署

新版韌體目錄為 `firmware-next`。目前裝置實機為 0.3.8；它以受控 USB 寫入非執行中 app 分區後切換啟動。舊 `firmware` 為先前 PlatformIO 版本，不可拿來當新版更新。

目前後端 0.1.5 與 GN100 Caddy 離線 fallback 已部署；韌體原始碼為 0.3.13，第二台仍為經 Mac USB 啟動的 0.3.12，並保存兩組不同 SSID；第一台仍為 0.3.8。0.3.13 尚待刷入第二台。接著驗證兩組 Wi-Fi failover、`/display` 管理、GPIO38、staged flash、離線安裝、實體 TFT／按鍵、大型 QR 與新版 live OTA。

## 從零開始：接線、連線與選擇更新方式

1. **實體 USB 連線**：使用可傳資料的 USB-C 線接開發板底部 USB-C 連接埠與電腦。只看到綠色充電燈閃一下不能證明資料線已連通；先執行 `python -m serial.tools.list_ports`，應出現 `/dev/cu.usbmodem...`，再以 `esptool chip_id` 確認是 ESP32-S3。沒有連接埠時先換資料線、USB 埠或移除集線器，不執行寫入。
2. **先嘗試外殼不拆、不按鍵的連線**：這台 ESP32-S3 使用原生 USB Serial/JTAG；正常插上資料線後，只要 `esptool chip_id` 能自動連線，就能進行受控讀取或寫入，不需要碰機殼內的 BOOT／重置鍵。只有完全無法自動連線且已排除線材與 USB 埠問題時，才將拆殼按住 BOOT 視為最後救援方式。
3. **判斷部署方式**：原廠韌體、分區表不相容或裝置無法正常啟動時，依「首次安裝」做一次完整 USB 安裝。已裝有本專案雙 OTA 分區且能開啟設定頁時，只用 Tailscale OTA 更新應用程式，不再重寫 bootloader、分區表、NVS 或整片 Flash。
4. **正常 Wi-Fi 操作入口**：第一次開機掃螢幕 QR，手機加入 `ShiftAlarm-XXXX`，開啟 `http://192.168.4.1` 選擇 2.4 GHz Wi-Fi。連線成功後回到時鐘主畫面；用實體按鍵開啟 `更多資訊` → `手機設定`，掃描 `/calendar` QR。手機與裝置在同一區網即可使用 port 80，不需加入 Tailnet。
5. **Tailscale 入口**：先從區網設定頁開啟 `/tailnet`，按「加入／重新授權」，只在 Tailscale 官方登入頁登入。完成後裝置取得 `100.64.0.0/10` 位址；維護電腦也在同一 Tailnet 時可用 `http://<裝置 Tailscale IP>` 連線。裝置到辨識與更新後端固定走 `100.126.226.79:8237`。
6. **管理 Wi-Fi**：可在 `/display` 保存最多四組網路，新增或更新只在連線成功後提交。移除任何網路會立即中斷目前連線，提交移除後再從更新後的清單重新連線；移除最後一組會開啟配網熱點，不清除其他設定。也可同時按住「＋」與「－」十秒開啟熱點。

完整入口如下：`/calendar` 設班表與鬧鐘、`/display` 設方向／關屏／Wi-Fi、`/clock` 手動校時、`/tailnet` 管理 Tailscale、`/update` 從裝置頁啟動已發布更新。所有頁面使用裝置 port 80；內部 loopback 8081 不提供使用者直接連線。

## Caddy 離線 fallback 部署順序

1. 先更新後端，不先套用 Caddy fallback。
2. 後端 `/api/health` 通過後，由 Caddy 主機對預定 upstream 執行 `HEAD /device-offline`。必須收到 `200`、空 body 與離線頁專用 CSP；`/api/health` 契約保持不變，但不能單獨證明 fallback 頁存在。
3. 上述 readiness 通過後才更新 Caddy。設定生效後分別驗證裝置在線路由與 `/device-offline` 離線頁；任一失敗即保留既有 Caddy 設定，不繼續韌體更新。

## 每次改程式後的完整更新順序

1. `git pull --ff-only`，確認工作樹與遠端基準，將 `firmware-next/CMakeLists.txt` 的三段版本提高。
2. 載入 ESP-IDF 5.3.2 環境後執行 `idf.py -C firmware-next build` 與 `idf.py -C firmware-next size`，再跑 CI 所列的後端、排程、OTA、代理、Tailnet 與螢幕政策測試。實機版需要本機被 Git 排除的 `provisioning.h`；不得把 token 或帶憑證映像提交。
3. 只取 `firmware-next/build/xingzhi-cube-1.54tft-wifi.bin`。先用 `deploy/publish_firmware.py` 在私有目錄驗證映像，再傳至 `rpi-matrix:/home/kevin/DockerCompose/shift-alarm/`，於後端 `data/releases` 發布。
4. 使用 `deploy/ota_tailnet.py` 做唯讀預檢。裝置必須由 GPIO38 當下回報充電；它不是可靠 VBUS 偵測，充滿時即使接著 USB 也可能 fail-closed 拒絕。
5. 明確執行一次 `--download`。完成後不重開；確認 staged metadata，再另行執行一次 `--install`。兩個 POST 都不重試，也不自動串接。安裝只使用本地完整映像，不要求後端可達。
6. 等工具確認新版本回連並核對方向、關屏時間、班表模式、revision 與鬧鐘數。再實測主畫面、六項選單、四方向、長按關屏、單次喚醒、配網 chord、更新資訊頁、校時及一次測試鬧鐘。

實際命令範本：

```sh
idf.py -C firmware-next build
idf.py -C firmware-next size

scp firmware-next/build/xingzhi-cube-1.54tft-wifi.bin \
  rpi-matrix:/home/kevin/DockerCompose/shift-alarm/firmware-新版本.private.bin
scp deploy/publish_firmware.py \
  rpi-matrix:/home/kevin/DockerCompose/shift-alarm/deploy/publish_firmware.py
ssh rpi-matrix 'chmod 600 /home/kevin/DockerCompose/shift-alarm/firmware-新版本.private.bin && \
  cd /home/kevin/DockerCompose/shift-alarm && \
  python3 deploy/publish_firmware.py firmware-新版本.private.bin --release-dir data/releases'

python3 deploy/ota_tailnet.py \
  --device http://裝置的-Tailscale-IP \
  --backend http://100.126.226.79:8237 \
  --token-file /私有路徑/device-token.txt \
  --version 新版本

python3 deploy/ota_tailnet.py \
  --device http://裝置的-Tailscale-IP \
  --backend http://100.126.226.79:8237 \
  --token-file /私有路徑/device-token.txt \
  --version 新版本 --download --wait-seconds 900

python3 deploy/ota_tailnet.py \
  --device http://裝置的-Tailscale-IP \
  --version 新版本 --install --wait-seconds 900
```

`device-token.txt` 權限必須是 `0600`。若預檢或安裝失敗，先讀取 `/api/status`、`/api/tailnet` 與 `/api/update`；不要立刻重送安裝、改走區網後端或執行 `erase-flash`。裝置完全無法啟動時才回到 USB 救援流程。

## 首次安裝

首次從原廠或 0.1.x 遷移，需要 USB 安裝新版引導程式、分區表與應用程式。先識別目前連接的晶片／MAC／Flash／PSRAM，對這一台保存完整備份；不可將另一台的原廠備份或 Tailnet 身分當作這一台的備份。Flash 中可能有密碼與身分私鑰，備份與帶憑證韌體不得公開。

目前原機已經使用原廠 [線上燒錄頁](https://upload.nologo.tech/) 恢復；先前 USB 中斷原因未確認。此事不代表已證實硬體燒毀，也不代表之後寫入保證沒有中斷。出現寫入錯誤就停止，先確認連接與原廠救援模式。

編譯測試與元件測試，不等同首次安裝或實機更新測試。必須完成硬體驗收後，才可記錄為可用版本。

## 後續更新

1. 修改程式並提高 `firmware-next/CMakeLists.txt` 的三段數字版本。板型固定 `xingzhi-cube-1.54tft-wifi`。
2. 使用 ESP-IDF 5.3.2／Arduino 3.1.3 建置，執行後端、OTA 政策、代理串流及 Tailnet 測試並完成審查。保留建置設定與摘要。
   首次部署時將 `firmware-next/main/provisioning.example.h` 複製為被 Git 排除的 `provisioning.h`，填入後端 `DEVICE_TOKEN` 並移除範本的編譯阻擋行；不填入 Wi-Fi 密碼、New API 金鑰或另一台的 Tailnet 身分。`provisioning.h` 與其建置出的韌體均視為私密檔案。
3. 使用應用程式 `.bin`，不能使用整片 Flash 備份、引導程式或合併映像。檔案最多 4 MiB。
4. 將應用程式與 `deploy/publish_firmware.py` 傳至後端主機的私有目錄。以容器的同一 UID `1000` 執行發布，確保容器可讀取；工具建立的目錄為 `0700`、檔案為 `0600`。

```sh
python3 deploy/publish_firmware.py /私有路徑/應用程式.bin --release-dir /home/kevin/DockerCompose/shift-alarm/data/releases
```

工具驗證板型、版本、分段校驗、內建 SHA-256 與大小，先保存不可變摘要檔案，再原子切換 `active.json`。版本必須遞增；同一映像重跑不會重複改動。此步僅發布，裝置不會自行安裝。

5. 在 `/update` 先按 `下載更新`。只有 `/api/update` 的 `canDownload=true` 才能操作；下載完成不重開。
6. staged metadata 出現後，按 `安裝並重新啟動`。只有 `canInstall=true` 才能操作；Wi-Fi、Tailnet 或後端不可達不會阻擋本地安裝，但充電、時鐘、排程與鬧鐘 guard 仍會阻擋。
7. `刪除已下載更新` 只清 marker，不擦除 app partition。部分下載不保存 marker，重新開機從 0 開始。
8. 新版通過本機初始化、自測與保存資料恢復後才確認版本。開機失敗回退仍依賴既有 rollback bootloader 與有效舊版。

Wi-Fi、方向、閒置關屏時間與排程保存在獨立設定分區；正常 OTA 不擦除此分區，不啟用 eFuse anti-rollback。四組 Wi-Fi 使用 `alarm_nvs` 內 A/B generation+CRC slots 與 checksummed active selector；新 slot 與 selector readback 成功後才套用，舊 slot 之後才清除。selector 結果不明時封鎖 mutation，reload 只接受 selector 明確授權且 generation 相符的 slot。NVS 目前未加密，密碼是裝置本機 plaintext-at-rest，不得輸出至 API、頁面或 log；固定 credential buffer 與 blob 會明確覆寫，但不保證 Arduino `String`／HTTP parser 的所有 heap copy 都可清除。Tailnet 身分保存在 NVS，重新授權只更新必要的節點憑證。方向與關屏時間使用同一筆 `display-v1` 資料寫入並讀回驗證；關屏選項為 1／5／15／30／60 分鐘或永久開啟。

後續更新通道規定與預檢／啟動命令見 [Tailscale OTA](Tailscale-OTA.md)。裝置必須實際可經原生 Tailscale 到達後端；不得以同 LAN 優先路由替代。既有本地更新頁只是操作介面，更新檔的下載通道仍須遵守此限制。


## 可重現的 USB 操作

以下以 ESP-IDF 5.3.2 的 Python 環境與 esptool 4.x 為準；連接埠請依當次實際裝置更換。先關閉占用序列埠的監視器。不要同時執行兩個刷寫程序。

```sh
python -m serial.tools.list_ports
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 chip_id
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 flash_id
# 私有目錄內備份本次連接的 16 MiB 裝置；不得公開此檔。
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 \
  --baud 460800 --after no_reset read_flash 0x0 0x1000000 device-private-backup.bin
chmod 600 device-private-backup.bin
idf.py -C firmware-next build
```

保存 `sdkconfig.defaults` 的 PPP 支援設定及 ESP-netif 相容性檢查。此設定用來隔離 SDK client-data，沒有啟用 PPP 網路；移除會重現先前的非 ESP-netif 指標解讀問題。不要停用編譯保護來繞過錯誤。

**僅第一次從原廠／舊分區遷移**，核對建置產物與分區配置後，在 build 目錄使用當次生成的 `flash_args`。這會寫入引導程式、分區表與初始 OTA 選擇資料，不能用於一般更新：

```sh
cd firmware-next/build
python -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 \
  --baud 460800 --before default_reset --after no_reset write_flash @flash_args
```

已有雙 OTA 分區的裝置，日常更新使用 [Tailscale OTA 工具](Tailscale-OTA.md)。必須以 USB 修復時，先讀取 0xe000 起 0x2000 位元組的 OTA 選擇資料並保存。兩個 4096 位元組 sector 的 sequence、state、CRC 分別位於 0、24、28。CRC 為 `binascii.crc32(sequence的4位元組little-endian編碼, 0xffffffff)`。只在兩筆狀態及執行分區可明確核對時繼續；損毀、待確認、回退或計數繞回情形不能猜測。

核對分區表後，先寫**非執行中**的 app 分區，等待 esptool 回報雜湊驗證成功；再寫入一個 OTA 選擇 sector，填入對應新 sequence、state=0（NEW）、CRC，其餘填 0xff。`(sequence-1)%2` 對應 app0/app1。不得覆蓋 NVS、另一個 OTA 選擇 sector、引導程式或分區表。實測 0.3.0 是 app1 0x410000、sequence 10；這只是該次紀錄，不是下次可盲抄的目標位址。

本板已驗證的啟動方式如下；保持 RTS 為 false，不使用先前造成啟動狀態混淆的 `hard_reset`／`run`。讀取啟動訊息後關閉連接埠：

```python
import serial, time
p = serial.Serial()
p.port = '/dev/cu.usbmodem1101'
p.baudrate = 115200
p.timeout = 0.2
p.dtr = False
p.rts = False
p.open()
p.dtr = True
until = time.monotonic() + 30
while time.monotonic() < until:
    # 訊息可能包含私人網路資訊，請在私有終端檢視。
    print(p.read(8192).decode(errors='replace'), end='')
p.close()
```

成功寫入不等於功能驗收：確認版本、螢幕、網路、方向、關屏時間、亮度、班表、校時與按鈕，再實測 Tailscale 資料通道。2026-09-13 的 0.3.1 已用 USB 部署；同日 0.3.2 已經由原生 Tailscale OTA 完整安裝。0.3.5 先確認 app0 正在執行，再把映像寫入 app1 並切換 sequence 14；0.3.6 再確認 app1 正在執行，把映像寫入非執行中的 app0（0x10000），驗證映像雜湊後只寫入 0xe000 的單一 OTA 選擇 sector（sequence 15、state NEW）。0.3.7 再確認 app0 正在執行，把映像寫入非執行中的 app1（0x410000），驗證後只寫入 0xf000 的單一 OTA 選擇 sector（sequence 16、state NEW）。0.3.8 再確認 app1 正在執行，把映像寫入非執行中的 app0（0x10000），映像 SHA-256 為 `171bb0500c9d59a4023545638b2d8b313262bbc593816925457c745171cdbb1c`，驗證後只寫入 0xe000 的單一 OTA 選擇 sector（sequence 17、state NEW）。這些更新都未碰 NVS、bootloader、partition table 或執行中的 app。0.3.8 重開後確認版本、Wi-Fi、Tailscale、90 度、5 分鐘關屏、25% 亮度、11 個上班日、07:20、連續班首日通知及 8 個有效鬧鐘全部保留；月曆依臺北時間把 9 月 13 日標為今天，網域與區網頁面內容一致。0.3.8 的短按中鍵關屏、任一鍵喚醒與響鈴任一鍵停止曾通過實機驗收；0.3.11 已把關屏改為中鍵長按放開，須另行實測。
